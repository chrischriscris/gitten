plait draws git history and diffs. Everything interesting about it follows from one constraint — core/ has no dependencies and no idea a UI is there — and from three rules that break ties when they disagree. This page runs the real algorithms: the code below is ported from plait-core and checked against it, line for line, on the same test inputs.

rule 1

Extensible

Anything a built-in does, an extension must be able to do too. Catch yourself hardcoding something a user might want to swap — make it a trait first.

rule 2

Beautiful and usable

Dense, quiet, keyboard-first. Not done until it looks like it belongs.

rule 3

Blazingly fast

Nothing on the render path allocates per frame or recomputes what a cache could hold. When the rules conflict, that order breaks the tie.

One file, six stages, live

A changed file goes from two blobs to pixels in six stages. Five of them are in core and could not name a UI if asked. Step through it — the payload below is the actual output of the actual stage, computed here in the browser.

The boundary

Three crates, and the line that matters

The interesting line is between the first two and the third. plait-git is the only crate that talks to a repository. plait-core is pure — no GPUI, no gitoxide, no I/O, and [dependencies] is empty on purpose, so it compiles in about a second and its tests need no window. plait-shell draws and takes input, and as little else as possible.

the rule

Two checks, both cheap against a diff

core has no dependencies. If something needs adding, the thing wanting it belongs in another crate.

A second frontend needs no logic of its own. core/examples/paint.rs draws a real diff — clipped, intraline-marked, syntax-coloured, themed — in 24-bit ANSI, and contains no pipeline code. When that stops being true, logic has leaked into the shell. It happened once already; the record is decisions/0007.

core/src/host.rs

Where the swappable pieces live

Built once in main.rs before any view exists, then held in a GPUI global and read on the render path — which is why plait.toml lands on the next frame instead of the next launch. A view that captures a clone instead will work, and will quietly not hot-reload.

The check: if a feature needs a knob that is not on Host or one of its fields, that feature is not extensible yet. The font used to be a const in main.rs with three things quietly depending on it; there is a test named after that mistake.

Stage 1 · acquisition

Two processes, whatever the diff size

Reads go through gix eventually; today everything shells out. Writes shell out permanently — push, pull, merge, rebase, commit — because that is what gets hooks, credential helpers, SSH agents and .gitconfig behaving exactly as they do in the user's terminal. Don't reimplement any of it; you will get it subtly wrong.

git/src/lib.rsrewritten, uncommitted

Why it fetches contents, not a diff

git diff will hand over a finished unified diff, and this crate used to parse exactly that. It no longer does: then git chooses the algorithm and plait_core::differ is decoration — a semantic or language-aware differ could never be reached, and rule 1 says a built-in may not do anything an extension cannot.

So acquisition is two lists of lines per changed file, and which lines correspond is decided in core afterwards. parse_unified_diff stays for reading .diff fixtures off disk, which is a different job.

the shape of it

Two processes, not one per file

git diff --raw -z -M --no-ext-diff HEAD~2..HEAD
:100644 100644 a1b2c3d 9f8e7d6 M core/src/differ.rs
:100644 100644 4c5d6e7 0000000 M shell/src/views/diff.rs
git cat-file --batch # every blob, one process

--raw names every changed path and both blob OIDs; cat-file --batch streams all of them in a single process. A git show per file is a process per file, which on a thousand-file diff is a second of fork before any work happens.

The OIDs are the reason to want it this way round anyway. A blob's content never changes, so a diff keyed on the pair of them is cacheable forever. A null OID on the new side means the working tree — the file as it is on disk right now, which is the whole point of a diff with no revspec.

git/src/lib.rs · struct Pair

What crosses the boundary

One changed file as the two versions of its text. Vec<String> and not &str into one buffer, because the two sides come from different blobs and a rename means the paths differ too. Splitting into lines happens here rather than in core, so the lossy UTF-8 decode — I/O's problem — stays on this side.

Never read_to_string anything from git

Commit metadata is not guaranteed UTF-8 and real history carries Latin-1 author names — git/git panics it outright. Read bytes and String::from_utf8_lossy. Never fail to show a repository over one bad byte.

Binary is a thing to say, not to skip

A NUL byte on either side sets binary, and the file is modelled as a file with no hunks rather than dropped: the diff still has to report that it changed, and "binary" is the honest thing for it to say.

Stage 2 · core/src/differ.rs · decisions/0001

Which lines correspond is a judgement call, not a fact

Myers minimises the edit count. Histogram anchors on rare lines. A semantic differ would ignore both and compare syntax trees. So it is a seam, not a function — and an implementation produces only the edit script. Line numbers, context, hunk headers and the @@ … @@ fn name suffix are shared by every differ, because that bookkeeping is identical for all of them and getting it subtly wrong in a second place is exactly the kind of bug nobody sees until a header points at the wrong line.

the contract
pub struct Edit {
old_start: u32, old_end: u32,
new_start: u32, new_end: u32,
}

Replace old[old_start..old_end] with new[new_start..new_end]. An empty old range is a pure insertion, an empty new range a pure deletion, and both empty never happens. Sorted by old_start, non-overlapping, and never two adjacent. u32 because a diff of more than four billion lines is not a diff, and 16 bytes per edit keeps a large file's script in cache.

the guards

Both worst-case quadratic in the differing lines

Every recursion is bounded by MAX_STEPS = 40_000_000 and degrades to a whole-region replace rather than stalling the load. 50k lines against 50k different lines is 1010 steps — minutes. Past the budget the honest answer is "this file was replaced", which is what the diff would have looked like anyway.

Recursion is an explicit stack, not the call stack. A 50k-line file whose every anchor peels off one line is a 50k-deep recursion — a stack overflow rather than a slow load, and not a hypothetical shape: a generated file with a repeating structure produces exactly it.

histogramthe default

Anchor on the rarest line, recurse either side

A line that appears once is almost certainly the same line. A } appearing four hundred times tells you nothing. So each candidate run of matching lines is scored by its rarest line and the lowest score wins, with a longer run breaking the tie. That ordering is the whole of histogram diff.

Both halves of that are wrong in the plausible direction, which is why they are worth reading twice. Score a run by its most common line instead and a four-hundred-line run of unique code loses to a one-line run the moment a single } falls inside it — measured on this repository, that cost 582 spurious changed-line pairs on one 690-line file. And the threshold has to tighten as the search runs: once a run scoring 2 is in hand, a line appearing forty times cannot be part of anything better. Without that, a longer run wins on length alone however common its lines are, and this repository's whole history came out 10 changed lines worse than git diff --histogram over 9,958.

MAX_ANCHOR_OCCURRENCES = 64. Git's xdiff uses 64 for the same purpose and the same reason, and matching it means a diff of the same file looks the same in both tools. A region with lines in common but nothing rare enough — or one that has run out of step budget — is handed to Myers: the case histogram exists in order not to guess at goes to the algorithm that does not guess.

why not Myers, which git defaults to

A minimal edit script is not the same thing as a readable one. Myers is free to match any } to any other }, so a block moved down a file dissolves into a mesh of one-line changes. Anchoring on lines that appear exactly once means a function signature becomes the anchor and the moved block reads as a move.

Diverging from git's default means a diff here can differ from git diff on the same commit. That is intended; both are correct, one is easier to read. Patience is the same traversal with the rarity threshold at one, kept under its own name because the difference is visible on real code: a file with three identical impl Default for blocks gets anchored by histogram and not by patience, and which reads better depends on the file.

core/src/differ.rs · fn hunks, fn header

Grouping

Grow the group while the next change is close enough that the context between them would be printed anyway — splitting there would emit the same lines twice under two headers, which is what git avoids too.

The same lead both sides

Take context lines off both sides together. Taking it from each independently drifts the two cursors apart at the top of a file.

git's two odd conventions

Byte-for-byte what git writes, including the two that look like mistakes: a count of 1 is omitted, and a count of 0 prints the line before the change rather than the line at it.

The header's tail

git's default rule and nothing cleverer: a line starting with a letter, _ or $ is a declaration, anything indented is inside one. Wrong on plenty of languages, right often enough to be worth four lines — and a language that cares can ship a Differ that writes its own headers.

Correctness is checked against git rather than argued. A minimal edit script has exactly one length, so myers must match git diff --minimal exactly — that is what git/examples/diffcheck.rs runs over real history, from ./check.sh. The three algorithms on this page were checked the same way: 162 edit scripts over 54 real file pairs from three repositories, against the Rust, byte for byte.

Selection is by name. host.differ.select("myers"), host.differ.route(&["json","lock"], "myers") — a &'static str on the trait rather than a wrapper's business, because a config file has to be able to express it and decisions/0012 says the config file holds data, never behaviour.

Stage 3b · core/src/lib.rs · decisions/0008

The second pass: which words inside the line

Line diff first, then re-diff only the pairs a line diff already matched as a replace. That is why a plain quadratic LCS is the right call here: the inputs are one line each, not one file. replace_pairs matches a run of N removals to the M additions that follow it, by position, and min(N,M) pairs go to the word diff.

The LCS table is a × b cells. Dice coefficient over tokens, 2·LCS / (len_a + len_b). The LCS table is already built, so its corner gives the similarity for free. Below the floor the pair gets no word highlighting at all — the line keeps its add/remove background.

Words, not characters. A char diff of code highlights every bracket and reads as confetti. And spans close over whitespace-only gaps, because the LCS happily matches the space between two changed words — every space punched a hole in the highlight, so a rewritten sentence drew as a row of separate blocks with the background showing through.

The floor is six lines and removes the damage now. Both can be true. Meanwhile core/src/align.rs makes the same positional guess the one place it has to be shared, because a side-by-side view and the intraline pass must agree or a row shows a removal beside an addition whose highlighted words were computed against a different line.

Stage 3c · core/src/syntax.rs · decisions/0003, 0004

Colour, without a parser

A scanner that knows no languages, plus a table per language, plus a router that picks an implementation per path. lex makes one pass over bytes and understands exactly five shapes: line comments, block comments, strings, numbers, words. Everything language-specific is data — eighteen tables covering forty-three extensions and whole filenames, which is how Cargo.lock reaches a table at all.

the router
path + lines
│
Highlighters ─── route "md" ──► Markdown line-oriented, its own code
(router) ─── route … ──► your impl tree-sitter, LSP, anything
└── fallback ──► Lexer → Languages: path → Syntax table

Last route wins, so a built-in table can be corrected rather than only added to. set_fallback replaces the scanner for everything unrouted, and languages() then returns None — there are no tables to register with any more. A tree-sitter highlighter takes exactly the languages the scanner cannot do, in its own crate, with its own dependencies, none of them reaching core.

the invariant that cost three tests

A byte whose opener matched but whose rule declined must still advance the cursor

An apostrophe in HTML prose, a # inside ${x#y}, the / that closed a comment. Three tests hung on this before the fallback existed.

The other half of the speed: a first-byte table, opens: [bool; 256], built with the Syntax, so any byte that cannot open anything skips the whole rule walk. Worth about 2× on every language measured.

Why not a parser

A diff hands you fragments, which is the input a parser is worst at: error recovery is its slow path, and the recovery loses spans. The scanner has no parse context to lose, so fragmentation costs it nothing measurable.

core/src/syntax.rs · Markdowndecisions/0004

The second implementation, and the proof the trait is worth having

Prose has no keywords, an apostrophe is not a string, and what is worth colouring is structure. The table-driven attempt mis-coloured 21.8% of every file — the worst result of any language, by a factor of two. The model was wrong, not the table.

So: 100 lines that walk lines instead of bytes. ATX and setext headings, fenced code (the one piece of state that crosses lines), blockquotes, thematic breaks, list markers, then inline code, emphasis, strong and links. Unclosed delimiters are left as text — in a diff a line often is half a construct, and an unmatched * is far more likely to be a bullet than the start of emphasis.

12 kinds, indexed not matched

Small on purpose: these are the classes a scanner can identify without a parse, and a dense diff should not wear more colours than this. The four prose kinds live in core rather than inside the Markdown highlighter, because a theme has to be able to style them without knowing which highlighter ran.

Multi-line constructs, and the one-side rule. lex_lines joins the lines, scans once, then splits the tokens back per line, clipping any that cross a boundary — a doc comment or a multi-line string is several rows in a diff and lexing each row alone would lose it. And the old and new lines of a hunk are two different texts that happen to be printed interleaved, so each side is scanned separately through for_each_side and context lines — which belong to both — are scanned twice. Scanning them as one splices a removed line into an added one and produces text that was never valid in any language.

core/src/lib.rs · shell/src/graph.rs · decisions/0002

Lanes, hues, and a hard cap at twelve

Lane assignment is pure and lives in core; geometry and painting live in the shell. The split is not cosmetic — lane assignment is where the bugs are, and it is testable without opening a window. One vector of "which sha is this lane waiting for", walked newest-first.

state after this row

topological order is mandatory

Always log with --topo-order. It is what git itself uses for --graph, and assign_lanes assumes it: without it branches interleave and the drawing is simply wrong.

It is not a width optimisation. It narrows git/git from 417 lanes to 280 and widens cmux from 19 to 73. Correctness, not compactness.

Two invariants, asserted on real history

  • A commit's first parent continues on the same lane — unless an earlier commit already claimed that lane for the same parent, which is a legitimate collapse.
  • A merge's second and later parents never land on the merge's own lane.
colour belongs to the branch, not the column

Colouring by lane index is the obvious thing and it is wrong: lane 1 is recycled the moment a branch merges, so unrelated branches come out the same blue and read as one long-running thing. Toggle hue per branch off above to see it.

So Hues walks the history and hands each new lane the next hue on the wheel, skipping any hue a concurrently live lane holds, and releases it when the branch ends. LANE_HUES = 6 is the size of that ledger — how many live branches can be told apart at a glance — and is not the number of colours a theme ships. A hue resolves through theme.lane(hue), which cycles over whatever the theme provides.

the capdecisions/0002

MAX_LANES = 12, hard. git/git reaches 280 concurrent lanes, which at LANE_W = 14px is a 3,920px gutter — it pushes the commit subject entirely off screen. Nobody reads past a dozen; git's own --graph is unreadable well before that.

Lanes past the cap collapse onto the last column in theme.lane_overflow grey, so the overflow reads as "there is more over here" rather than being silently misdrawn. They collapse in the data too, or git/git would queue 280 identical quads per row.

Why not scale the lane width down? Sub-pixel lanes stop being crisp, and 280 hairlines is not more legible than 12 lanes and a grey column.

shell/src/graph.rs · the drawing

row_draws flattens each row once, at load, into what painting needs — so the paint callback never touches the commit list. One canvas() per row, so the drawing virtualizes with uniform_list for free.

  • Verticals are quads. A vertical line is a rectangle, and a quad costs a fraction of a tessellated stroke path.
  • Curves are half an S each. A curve touches its lane on the dot line and crosses the row boundary halfway to its partner, where the next row picks it up. Each half runs OVERSHOOT = 0.5px past the boundary along its own tangent — collinear, so it cannot kink — because two antialiased butt caps meeting exactly leave a visible crease.
  • A dot is one quad with corner radii at half its size, which is a circle, and the shader antialiases it better than tessellation would. The middle is punched out with theme.chrome.bg, so lines pass behind a node and the graph reads as holes in the sheet.

per-row width, and the row itself

Each row's gutter is measured from its own lanes, not the widest row in the repository, so a commit alone on the trunk gets nearly the whole window for its subject. Widths are measured in whole lanes so text steps on the lane grid: ragged by a column reads as "the graph is wider here", ragged by three pixels reads as broken.

core/src/theme.rs · decisions/0005, 0009

A token is never drawn on "the background"

A theme is a struct of 0xRRGGBB numbers plus two booleans — no GPUI, no Hsla, nothing a terminal could not read. That is the test: a palette only one frontend can read is a palette in the wrong crate. The ANSI painter and the GPUI window read the same numbers.

But a diff draws on five different surfaces, and two of them are much lighter. The comment grey that reads as pleasantly quiet on the file body measured 1.15:1 against the old changed-word background — a grey smear on green, which is how a screenshot found it. WCAG AA for body text is 4.5.

every kind × every surfaceported from theme.rs hover a cell
min_contrast floor 3.5

Resolution is not per frame. readable costs six powf per call and render asks for a style per run per visible row per frame, so the whole 12 × 5 table is computed once in rebuild() and render is one index. The consequence to remember: after mutating syntax, diff or min_contrast directly, call rebuild(). set_syntax does it for you.

fn readable

Blend, don't substitute

readable returns the colour untouched if it already clears the target. Otherwise it blends toward white — or black, if the background is light — in 24 steps, stopping at the first that clears. Blending keeps the hue: a lifted comment is the same grey-brown, just far enough off the background to read.

Themes therefore only have to be tasteful. They never enumerate a colour per surface; the floor guarantees the rest.

The shipped floor is 3.5, not 4.5. A diff wants its comments to recede, and lifting them to 4.5 makes them louder than the code around them. Drag the slider and watch the comment overtake the keywords.

The lift alone was not enough. Taking the comment all the way to #b7b3b0 made it the loudest thing on the line, so the changed-word backgrounds were darkened in the same change: #2c5c33 → #1e3a23 and #6b2f2a → #43201a.

every colour the app draws

If a colour is not here, it is a bug — there were 35 hex literals across four shell files before this existed.

Weight and slant are in Style because emphasis in prose is not a colour: a Markdown **word** that only changed hue would be wrong. Lane and author colours cycle, so a theme may ship three or twelve, and an empty list falls back to chrome colours rather than panicking.

shell/src/config.rs · plait.tomldecisions/0012

Changing it without a rebuild

Colours, the font family and the font size are read on the render path, so a saved plait.toml lands on the next frame — no rebuild, no relaunch, no lost scroll position. That is the payoff for colour having been data in a dependency-free crate all along.

The file is read forgivingly, because it is re-read on every save of something you are in the middle of typing: an unparseable file leaves the theme exactly as it was, and a single bad line is named and skipped while the rest applies. A warning only appears when a value actually changed — one that fires on an unchanged value teaches you to ignore the ones that matter.

Data only. Never behaviour.

Not a stylistic preference: a settings panel has to rewrite this file in place, keeping comments and key order, and it cannot round-trip a function. So a keybinding names its command and the behaviour lives in a plugin file the format only ever points at.

Which is also why there are no computed colours. When a field is only ever "that one, but lighter", derive it in Theme instead of asking the file for it — rebuild already does exactly that for every syntax colour on every surface. Two fields cannot reload live and say so: font.monospaced, because table padding rewrites row text during prepare, and font.advance, because the widest-row guess is made once at load.

Stages 4–6 · shell/src/views · decisions/0006, 0010

Rows, at eight bytes each

The diff view used to flatten every file into a closed enum Row and draw it with a match. A different presentation for one file type meant editing that enum and that match. Rule 1 says an extension must be able to do what a built-in does — and the obvious fix breaks rule 3, because Vec<Box<dyn Row>> is one allocation per row and the deletion fixture has 714,000 of them.

shell/src/views/diff.rs · trait Rows
pub trait Rows {
fn claims(&self, path: &str) -> bool;
fn len(&self) -> usize;
fn build(&mut self, file: prepared::File);
fn render(&self, i: usize, host: &Host) -> AnyElement;
fn width(&self, i: usize) -> usize;
}

Each file goes to the implementation that claims its path; the last registered claimant wins, and TextRows claims everything, which is what makes it the fallback. MarkdownRows is the second built-in and takes .md, .markdown and .mdx — registered through the same call an extension would use, because a built-in that skips the seam leaves the seam untested.

SplitRows is the third, and the one that pays for the seam: a two-column diff sounds like a different view and is a different presentation. It claims every path, takes the same prepared lines, and draws them in two columns — no new trait, no new argument, no edit to TextRows. A shell-side Layouts registry holds the whole-diff presentations and s cycles them; host.layout is which one the window opens in.

It cost the theme exactly one colour: diff.absent_bg, for the half of a row with no line in it. Its own field and not context_bg, because the two mean opposite things — context is a line that did not change, and this is the absence of a line. Flatter and darker than every other row background, so a run of them reads as a hole in the column rather than as content. That is what "every colour the app draws lives in Theme" costs when it is kept honest: a new presentation adds a field, not a hex literal.

the order table
struct RowRef { owner: u16, index: u32 } // 8 bytes

Implementations keep their own row storage; the list keeps only which implementation owns each row and where in that storage it sits. At 714k rows a boxed row is 714k allocations to build and to chase on every scroll, against 5.7 MB of flat index table. The indirection would land exactly where it hurts most — the render path — for no expressive gain.

The constraint to design around: row height is fixed for the whole list, because uniform_list is the only reason a 714k-row diff scrolls at all. You may draw anything within ROW_H; you cannot ask for more. A presentation that genuinely needs variable height — a reflowed Markdown preview, a side-by-side image diff — wants a pane.

fn runs — the only thing that runs per frame click a row

Syntax sets the foreground, intraline sets the background, and the foreground is resolved against whichever background it lands on. Both inputs are already sorted and internally non-overlapping, so this is a sweep over their combined edges rather than a sort — one StyledText with a run list, never an element per span.

The run list is rebuilt per visible row per frame, and that is a deliberate exception to "recomputes what a cache could hold": caching it for 714k rows costs roughly 40× the memory of the rows themselves, and 50 rows × ~15 runs is nothing. Rows hold SharedString, not String — handing GPUI a String copies the line every frame.

core/src/markdown.rs · MarkdownRowsdecisions/0010 edit the line

The markers are found from the tokens, not by parsing

By the time a row reaches lay_out, the Markdown highlighter has already emitted a Strong token over **word** and a Link over [text](url) — delimiters included, because a token is a range of the source. So the set of bytes to hide is derivable from ranges that already exist, by checking the bytes at each end of each token. No second scan, and no parser.

try

Deriving it from the bytes rather than from the token's provenance is what keeps it correct if .md is routed elsewhere: a tree-sitter highlighter puts Strong over different ranges, and the check is "does this token begin with two asterisks", so the answer stays right. A Strong token wearing no delimiters keeps every byte it has, and there is a test for exactly that.

what fits inside 22 pixels
  • Font size is a row property, not a run property. GPUI's HighlightStyle carries colour, weight, slant, background, underline, strikethrough and fade — and is documented as "a single font, uniformly sized and spaced text." There is no size on a run. So a heading scales by .text_size() on the row and never within one, and the ceiling is ROW_H / 1.2 — about 18px — past which it clips into its neighbour.
  • Leave the row background alone. In a diff it means added or removed, and that is the one thing a presentation may not spend. Group rows with a bar down their left edge instead.
  • Punctuation you draw yourself is furniture, not text. A bullet glyph inside the string becomes a run in the merge and takes the text's colour; as its own div it carries its own. It also keeps every text rewrite a pure deletion, which is what lets the range remapping stay one-directional.
  • Row count is not yours to change. The gutter shows both line numbers and they have to keep adding up, so a blank line still costs a whole row — 9% of the book fixture, 30% of a technical-docs tree. A test asserts both presentations produce the same count for the same file.
the ordering trap, twice

Clip before both passes, so no span or token can point past what will be drawn. Reversed, the renderer indexes a line by a range that no longer exists in it: a panic in a debug build, mojibake in a release one.

Move the ranges before cutting the text, because both have to be in the same coordinates while the mapping is computed. Reversed, a token indexes bytes that are gone. Same failure mode, same kind of test pinning it.

And the sharp edge that drew blood: for_each_side hands a context row to its caller twice, because a context row belongs to both sides. The token pass does not care — assigning twice is assigning once. The table pass mutates, and padding an already-padded row is not idempotent: the first pass wrote a │, the second measured the grid it had just drawn and then panicked splitting that three-byte glyph at byte 1. The fix is structural — measure every grid first, rewrite each row exactly once, added side winning for context rows.

Tables are the one construct whose cells must line up with the rows around them, so widths are measured per run of table rows and per hunk side. Padding wins over an element per cell because the render path is what rule 3 protects — and it only lines up in a monospaced face, which is what Layout::monospaced() is the frontend asserting. core cannot see a font, so it must be told.

shell/src/stats.rs · PLAIT_STATS=1

The overlay measures how fast we can redraw, not what the app costs at rest. GPUI is reactive and idles at zero frames, so the overlay requests an animation frame every render to force a continuous loop.

It is also a ceiling, not a throughput. GPUI paces animation frames off CVDisplayLink, so the fps reading is the display's current rate for as long as we stay inside its budget — and that rate is not a constant: Low Power Mode pins a ProMotion panel to 60 Hz, so the same binary reads 120 plugged in and 60 unplugged with nothing about the app having changed. Which is why best is on the line: the shortest interval in the ring, the one frame we know we made. If best and p50 agree, the fps figure is the panel's and not ours.

honesty section

Not built, and moving right now

Listed so nobody reads an intention as a description. A doc describing an unbuilt feature is worse than no doc, because it costs a reader real time before they find out.

not built yet
  • cli/. Referenced throughout as the second door. paint.rs currently stands in for it as the proof that the boundary holds.
  • Command dispatch and the mode stack. Host is where they belong.
  • Extension loading. Every seam takes an implementation today; nothing loads one from outside the binary yet. "An extension" means code compiled in — the seams are shaped so that stops being true without them changing.
  • Writes. No commit, push, stage or rebase. Reads only.
  • gix. All reads still spawn git.
  • Panes. One view fills the window, which is why the Rows seam is row-shaped. A rendered Markdown row exists; a rendered Markdown document, reflowed and variably tall, is what needs the pane.
  • Code-block injection. A fenced block in a .md diff knows it said rust and is still drawn as one string.
code hot reload — investigated and rejected

The config file reloads data live and ./dev.sh removes everything either side of a code rebuild, but the rebuild itself remains: 3–5 s.

A dylib swap was rejected for reasons specific enough to be worth keeping. GPUI holds a thread-local element arena (a raw pointer, so a second copy allocates into nothing), a process-wide entity id counter, and forty uses of TypeId::of for global and entity lookup. A dylib that statically links its own gpui forks all three.

The fix is making gpui a real dylib and building with -C prefer-dynamic the way Bevy does — possible, multi-day, and broken by every gpui update. Dioxus's subsecond hot-patches the binary instead and sidesteps the ABI problem entirely; that is the direction to watch.
