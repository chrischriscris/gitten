gitten a desktop git client — architecture & algorithms

gitten

A desktop git client with lazygit's keyboard model, written in Rust on GPUI. It is a reader: it acquires, parses, prepares and draws git data — commits and diffs — as fast as it can, with every stage testable without a window.

Three rules, in priority order

1. Extensible

Anything a built-in does, an extension must be able to do too. Hardcoding something a user might want to swap means making it a trait first. Every seam is exercised by a test that swaps the implementation.

2. Beautiful & usable

Dense, quiet, keyboard-first. Not done until it looks like it belongs. Colour is data; contrast is resolved, not guessed.

3. Blazingly fast

Nothing on the render path allocates per frame or recomputes what a cache could hold. The render path is one StyledText per visible row.

The one architectural rule

core/ never knows a UI exists.

No GPUI, no rendering, no terminal, and [dependencies] is empty — deliberately. core compiles in a second and its tests need no window. Everything except drawing and input lives there: git parsing, lane assignment, diffs, the extension host.

Two cheap checks keep it honest: core/Cargo.toml ends with an empty [dependencies], and a second frontend (examples/paint.rs, ANSI) draws a real diff with no pipeline code of its own.

The diff pipeline

From git diff bytes to pixels, in six stages. Five are in core and have no idea a window exists.

1
Acquire gitten-git
gitten_git::diff → bytes

Reads bytes — never read_to_string, because commit metadata is not guaranteed UTF-8 and real history carries Latin-1 author names.

2
Parse core
parse_unified_diff → Vec<FileDiff>

Walks unified output into FileDiff → Hunk → DiffLine, tracking both line numbers. Binary files, renames and mode changes are skipped rather than modelled — a gap, not a design.

3
Prepare core
prepared::prepare → Vec<prepared::File>

One pass, in this order, because each step depends on the last.

a
Clip

Every line to a column budget (MAX_LINE_CHARS = 2000). Clipping comes first so no span or token can ever point past what will be drawn — get this backwards and the renderer indexes a line by a range that no longer exists. Real repos contain minified bundles; a 9.6-million-character line was measured in the wild.

b
Intraline — second pass only

Line diff first, then re-diff only the pairs a line diff already matched as a replace. replace_pairs matches a run of removals to the additions that follow it, by position. Two guards: MAX_INTRALINE_TOKENS = 1000 (the LCS table is a×b cells) and MIN_INTRALINE_SIMILARITY = 0.4. Words, not characters — char diffs on code are confetti.

c
Syntax — per hunk side

The old and new lines of a hunk are two different texts printed interleaved; scanning them as one splices a removed line into an added one. Each side is scanned separately, and context lines — which belong to both — are scanned twice.

4
Build shell
Rows::build, per file → renderer-owned rows

Each file goes to the Rows implementation that claims its path; the last registered claimant wins, and TextRows claims everything, which makes it the fallback. MarkdownRows takes .md, .markdown, .mdx.

a
Layout (optional)

markdown::lay_out, only if the renderer asks. Returns what each line structurally is and rewrites each line so its markers are gone and every token and span still indexes it. Removal is deletion only — String::drain back to front, nothing allocates per row. Tables are the exception: column widths are measured per run, then each row rewritten once to the grid. 70–100 ns a row.

5
Order shell
Vec<RowRef> — 8 bytes per row

struct RowRef { owner: u16, index: u32 }. Implementations keep their own row storage; the list holds only these 8-byte handles. At 714k rows a boxed row per row would be 714k allocations to chase on every scroll.

6
Draw shell
Rows::render + Theme → one StyledText per row

The only stage on the render path. One StyledText with a run list, not an element per span. Syntax sets the foreground, intraline sets the background, and the foreground is resolved against whichever background it lands on.

Anatomy of a line row

All rows the same height (ROW_H = 22px) so uniform_list can virtualize the whole thing.

12−fn draw(&self) { // later
12+fn draw(&self) { self.paint(1); } // now
13 let x = "hello";

Syntax sets the foreground, intraline sets the background (the highlighted words above), and the foreground is resolved against whichever background it lands on. Rows hold SharedString, not String, so render doesn't copy the line every frame.

The commit graph

Lane assignment is pure and lives in core; geometry and painting live in the shell. The split is not cosmetic — lane assignment is where the bugs are, and it is testable without a window.

Interactive: lane assignment

One vector of "which sha is this lane waiting for", walked newest-first. First parent continues on the same lane; a merge's 2nd+ parents fork to new lanes; lanes converge when a commit satisfies several at once. Press Step to walk the history.

current commit waiting lane merge

Colour belongs to the branch, not the column

Colouring by lane index is the obvious thing and it is wrong: lane 1 is recycled the moment a branch merges, so unrelated branches come out the same blue and read as one long-running thing. So Hues walks history and hands each new lane the next hue on the wheel, skipping any hue a concurrently live lane holds, and releases it when the branch ends. LANE_HUES = 6 is the size of that ledger.

The cap

MAX_LANES = 12, hard.

git/git reaches 280 concurrent lanes — a 3,920px gutter that pushes the commit text clean off the screen. Lanes past the cap collapse onto the last column in theme.lane_overflow grey, and collapse in the data too, or git/git would queue 280 identical quads per row. Overflow is visible rather than silently misdrawn.

Per-row width

Each row's gutter is measured from its own lanes, not the widest row in the repository. A commit alone on the trunk gets nearly the whole window for its subject. Widths are measured in whole lanes so text steps on the lane grid — ragged by a column reads as "the graph is wider here", ragged by three pixels reads as broken.

Drawing

Verticals are quads

A vertical line is a rectangle — a quad costs a fraction of a tessellated stroke path.

Curves are half an S

Each half runs OVERSHOOT = 0.5px past the boundary along its own tangent (collinear, so it cannot kink) because two antialiased butt caps meeting exactly leave a visible crease.

A dot is one quad

With corner radii at half its size — which is a circle — and the shader antialiases it better than tessellation. The middle is punched out with the chrome background, so lines pass behind a node and the graph reads as holes in the sheet.

One canvas per row

So the drawing virtualizes with uniform_list for free. row_draws flattens each row once at load into RowDraw { lane, hue, is_merge, lines, curves, width }.

Syntax highlighting

A scanner that knows no languages, plus a table per language, plus a router that picks an implementation per path.

Highlighters (router)

Routes each path to an implementation. route("md") → Markdown, route(...) → your impl, fallback → Lexer.

path + lines▼
Lexer → Languages → Syntax

One pass over bytes, appending non-overlapping Tokens. Understands exactly five shapes: line comments, block comments, strings, numbers, words. Everything language-specific is data.

lex() / lex_lines()▼
Vec<Vec<Token>>

One list per line, ranges relative to that line, sorted, non-overlapping, on char boundaries.

The scanner

Per position it tries, in order: line-comment openers, block-comment openers, string openers, digits, word characters. A first-byte table (opens: [bool; 256], built with the Syntax) skips the whole rule walk for any byte that cannot open anything — worth about 2× on every language measured.

The one non-obvious invariant

A byte whose opener matched but whose rule then declined must still advance the cursor. An apostrophe in HTML prose, a # inside ${x#y}, the / that closed a comment. Three tests hung on this before the fallback existed.

Building a table

Syntax::new()
    .line(&["//"])
    .block(&[("/*", "*/")]).nested_block()
    .strings(&[("r#\"", "\"#", false, true), ("\"", "\"", true, true)])
    .keywords(&["fn", "let", "match"])
    .capitalized_types()
    .call_heuristic()
    .line_needs_boundary()
    .quote_after_eq()

Two rules the measurements forced

line_needs_boundary

# only opens a comment at line start or after whitespace. Without it, $# and ${x#y} paint the rest of every shell line. Stray colouring in a shell corpus: 0.99% → 0.82%.

quote_after_eq

In markup a quote only opens a string directly after =. Prose is full of apostrophes and none of them are strings. HTML: 6.2% → 2.5%.

Why not a parser

scannertree-sittersyntect
whole files104–262 MB/s7.1 MB/s0.4 MB/s
hunk-shaped fragmentsunchanged2.6 MB/s, a fifth of spans lost—
binary cost01.5 MB + 0.2–3.3 MB per grammar2.0 MB
bytes coloured40–67%66–89%—

A diff hands you fragments, which is the input a parser is worst at: error recovery is its slow path, and the recovery loses spans. The scanner has no parse context to lose, so fragmentation costs it nothing measurable (49.8 → 50.4 spans/KB). It pays for that in coverage and semantic classes — a call is a name before (, with no scope, resolution or injection.

Where the model breaks

Measured per language against tree-sitter as the oracle, ~900 KB of real source each:

  • Sound — 100% comment precision, ≤0.6% stray colouring: rust, go, java, kotlin, python, ts, js, json, toml, zig, c, c++, lua, css, swift, shell.
  • Under-colours, never lies — yaml and css unquoted scalars, C char literals and #include <...>: recall gaps with no bleed.
  • Breaks — html with inline <script>, php's <?php islands, markdown. These need injections, which need a parser. The last group gets no table rather than a wrong one.

Markdown, the second implementation

Markdown ships as a Highlighter of its own, not a table — the proof the trait is worth having. 100 lines that walk lines instead of bytes: ATX and setext headings, fenced code (the one piece of state that crosses lines), blockquotes, thematic breaks, list markers, then inline code spans, emphasis, strong and links. It emits Heading, Strong, Emphasis and Link.

Kinds

Twelve, indexed rather than matched so a theme lookup is one load:

CommentStrNumberKeywordTypeConstantFuncProperty HeadingStrongEmphasisLink

Small on purpose. These are the classes a scanner can identify without a parse, and a dense diff should not wear more colours than this.

Multi-line constructs

lex_lines joins the lines, scans once, then splits the tokens back per line, clipping any that cross a boundary. A doc comment or a multi-line string is several rows in a diff, and lexing each row alone would lose it. An unterminated single-line string stops at its newline; a language whose strings legitimately span lines (Rust) can run on, but only to the end of the text it was given — one side of one hunk.

Theming

A theme is a struct of 0xRRGGBB numbers plus two booleans. No GPUI, no Hsla, nothing a terminal could not read — which is the test: a palette only one frontend can read is a palette in the wrong crate.

Surfaces, and why one colour per class is not enough

A token is not drawn on "the background". It is drawn on one of five:

— Context       #0e0d0c — the near-black body of the file
—+Added       #16241a — an added line
—−Removed     #2a1917 — a removed line
—+AddedWord   #1e3a23 — a changed word inside an added line
—−RemovedWord #43201a — a changed word inside a removed line

The comment grey that reads as pleasantly quiet on Context measured 1.15:1 against the old changed-word background — a grey smear on green. So every class is resolved against every surface: theme.syntax_on(Kind::Comment, Surface::AddedWord) — one index, no maths.

Contrast resolution

pub fn luminance(c: Rgb) -> f32          // WCAG 2.1 relative luminance
pub fn contrast(a: Rgb, b: Rgb) -> f32   // 1.0 … 21.0
pub fn readable(fg: Rgb, bg: Rgb, target: f32) -> Rgb

readable returns fg untouched if it already clears the target. Otherwise it blends toward white — or black, if the background is light — in 24 steps, stopping at the first that clears. Blending rather than substituting keeps the hue.

The shipped floor is 3.5, not the WCAG 4.5

A diff wants its comments to recede, and lifting comments to 4.5 makes them louder than the code around them. It is one public field; raise it and call rebuild(). Themes therefore only have to be tasteful — they never enumerate a colour per surface; the floor guarantees the rest.

Cost, and where it is paid

readable costs six powf per call and render asks for a style per run per visible row per frame. So resolution happens once, in rebuild(), into a 12 × 5 table of Style. Render is one index. After mutating syntax, diff or min_contrast directly, call rebuild().

Changing it without a rebuild

gitten config > gitten.toml     # a complete, correct starting file

[font]
family = "JetBrainsMono Nerd Font Mono"
size = 14.0

[theme.diff]
added_bg = "#16241a"

[theme.syntax]
comment = "#615a52 italic"

gitten.toml is re-read every time it is saved, and colours, the font family and the font size land on the next frame — no rebuild, no relaunch, no lost scroll position. Two fields cannot reload live and say so: font.monospaced (Markdown table padding rewrites row text during prepare) and font.advance (the widest-row guess is made once at load).

The file holds data only — no expressions, no computed colours — because a settings panel has to be able to rewrite the file in place and cannot round-trip a function.

Extending

Rule 1 says anything a built-in does, an extension must be able to do too. Every seam is exercised by a test that swaps the implementation — one implementation and no test is a promise, not a seam.

The Host
pub struct Host {
    pub syntax: Highlighters,   // which highlighter each path gets
    pub theme: Theme,           // every colour the app draws
    pub font: Font,             // the face, and the numbers derived from it
}

Built once in main.rs before any view exists and held in a GPUI global. If a feature needs a knob that is not on Host or one of its fields, that feature is not extensible yet — that is the check.

The five seams

1. A language

Data, not code. Nothing about the scanner changes.

host.syntax.languages().unwrap()
    .register(&["nim", "nims"], Syntax::new()
        .line(&["#"])
        .block(&[("#[", "]#")]).nested_block()
        .keywords(&["proc", "var", "let", "type"]))

2. A highlighter

When the scanner's model does not fit — markup, scope, injections — implement the trait and route paths to it.

impl Highlighter for TreeSitter {
    fn highlight(&self, path: &str, lines: &[&str]) -> Vec<Vec<Token>> { ... }
}
host.syntax.route(&["html", "php", "vue"], TreeSitter::new());

3. A theme

Plain 0xRRGGBB throughout, so the ANSI painter and the GPUI window read the same one.

let mut theme = Theme::default_dark();
theme.set_syntax(Kind::Comment, Style::fg(0x93a1a1).italic());
theme.min_contrast = 4.5;
theme.rebuild();
host.theme = theme;

4. A font

Type as data, the same way colour is: a family name and three numbers.

host.font = Font {
    family: "Iosevka Term".into(),
    size: 15.0,
    monospaced: true,
    advance: 0.5,   // as a fraction of size
};

monospaced decides whether Markdown tables get padded into a grid; advance guesses which commit row is widest.

5. How a file's diff is presented

The Rows trait — the one seam whose registry is not on Host, because a Rows implementation returns an AnyElement and core never knows a UI exists. The list is an argument to Diff::with_renderers instead.

pub trait Rows {
    fn claims(&self, path: &str) -> bool;
    fn len(&self) -> usize;
    fn build(&mut self, file: prepared::File);
    fn render(&self, index: usize, host: &Host) -> AnyElement;
    fn width(&self, index: usize) -> usize;
    fn report(&self) -> String { String::new() }
}

Diff::with_renderers(files, host, vec![
    Box::new(TextRows::default()),       // fallback; must claim everything
    Box::new(MarkdownRows::default()),   // claims *.md
    Box::new(ImageRows::new()),          // claims *.png, wins over both
]);

What arrives in build is already clipped, intraline-diffed and highlighted — an implementation draws; it does not redo any of that. The constraint to design around: row height is fixed for the whole list, because uniform_list is the only reason a 714k-row diff scrolls at all.

What a new seam owes

  1. A trait or a data structure, not a match arm. The test is whether a second implementation can exist without editing the first.
  2. A registration point on Host, or on something reachable from it.
  3. A default that claims everything, so behaviour with nothing registered is the shipped behaviour.
  4. A test that swaps it.
  5. A line in AGENTS.md if it changes the philosophy, and a page in docs/ if it does not.
